# Discovery Prompt

Work read-only unless the user explicitly authorizes a discovery artifact to be written.

1. Require an explicit repository-root target path. Resolve real paths for target and harness. Apply `target.git_environment`: reject identity-affecting and unknown inherited `GIT_*` variables, remove known non-identity variables, construct only the approved child environment, neutralize count-based config injection, and reject unresolved local config includes. Resolve Git's canonical `--show-toplevel` under that environment and require it to equal the canonical authorized root. Compare canonical roots, common dirs, refs stores, object stores, transitive repository alternates, and shared ref/object device-inode pairs. Fail closed on any mismatch or unprovable independence. Establish one workspace execution policy bound to this canonical target and workflow; do not derive per-path write allowlists. Do not initialize or clone it.
2. Read target-local instructions through the selected component. Read ancestor instruction files only within an explicit canonical `workspace_root` chain, or from exact explicitly supplied canonical `instruction_roots` when no workspace root is given, and only from the policy allowlist. Without that input, do not read above target root. Resolve symlinks and refuse references outside authorized roots; do not enumerate arbitrary directories. Discover available skills/agent guidance; inspect purpose, scope, conditions, and side effects before applying any. Never install, download, or modify them without specific authorization.
3. Inspect the working tree and existing files. Audit code and documentation before proposing edits; preserve pre-existing work and confirmed decisions. Never silently replace or discard existing information.
4. Identify relevant source, tests, configuration, interfaces, project conventions, documentation conventions, and validation commands.
5. Report observed facts with file/line or command evidence. Label assumptions and gaps.
6. Separate requirements, inferences, confirmed decisions, optional improvements, and open questions.
7. Do not modify product code, requirements, or decisions during discovery. Decide routine engineering questions autonomously and record the rationale. Ask only about decisions that materially affect product behavior, cost, architecture, or operations. Continue independent analysis while a consequential question is pending.
8. Analyze proportionate scenarios before implementation: normal operation, invalid input, partial and external failures, timeouts/retries, duplicates/idempotency, concurrency, large workloads/resource limits, restart/persistence, cancellation/recovery, observability, and security. Mark irrelevant scenarios with a brief reason instead of silently omitting them.
9. Record each assumption with its rationale, impact if wrong, reversibility, and whether user confirmation is needed. Keep assumptions separate from verified facts and confirmed decisions.

Return: target ID/root, Git common/ref/object stores, workspace execution policy, baseline state, authorized instruction roots and discovered instruction records, applicable capabilities, relevant architecture, documentation condition, existing validation, authorization boundaries, explicit and implicit requirements, quality constraints, scenarios with expected behavior and verification, assumptions, decision recommendations, risks, open questions, and a bounded recommendation for the next phase. The orchestrator persists this discovery with the plan under the workspace policy.
